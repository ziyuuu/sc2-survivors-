## 基线与方法

实际 0.6.25 Web、命名单文件 HTML、源码及资源清单冻结在 `reports/local/7a-20261013/baseline/`。基线来自实际工作目录，不以较早 Git 提交替代。原始实验保存在同一主题目录内的独立子目录；失败和中间构建不覆盖。

测试主机为 Ryzen 7 5800U / Radeon，Chrome，1440×900、DPR 1、原画质。每次记录构建哈希、浏览器和 GPU 信息。新浏览器上下文不等同于操作系统或驱动冷缓存。正式计时、CPU 分析、细分诊断和 GPU 查询分开，异步编译的等待时间不称为 GPU 耗时。

浏览器 `Runtime.getHeapUsage` 分别记录 JS 堆和外部 backing storage；离线页的 `performance.memory` 可被量化为固定 10 MB，不能据此判断真实内存。显存没有可靠直接测量，不把纹理字节或进程内存当成显存实测。

## 已确认的热点和候选

1. 原生着色器首用与驱动同步：首个细分样本中 685 次 `getProgramInfoLog` 合计约 65.6 秒。禁用成功日志后，大量时间转移到 uniform 查询及纹理提交，说明不能将 API 名称直接当作可消除的 CPU 工作。`gl.finish` 在该样本中约 0.1 毫秒，不作为主要优化目标。
2. 原始动画准备：同一动作的骨骼及多个武器挂点重复推进 Mixer、更新节点；首个细分样本约 6 秒。候选为共享一次姿态采样，以及在同一算法上加入主线程让出。必须保持全部 24 FPS 采样、半精度矩阵字节、双精度挂点、动作映射和归一化结果。
3. 菜单期间的可选 GPU 预热会形成数秒同步阻塞。比较缩短开场准备，以及可选阶段只保留资源读取与模型 CPU 准备、将 GPU 工作留给正式入口。离线解包在当前记录中尚未证明比这些路径更值得改动，不因预先列入候选就直接引入 Worker 或长期解码缓存。

着色器候选 A 仅在失败时读取详细日志，并保留所有程序的链接成功校验。候选 B 提前编译实际深度通道，并保留真实 HDR、阴影、接触阴影、折射与最终首帧验证。两者各完成五次交替对照：A 两次、B 三次的首十秒 P95 约 33 毫秒，同组五个原实现样本为 16.8–16.9 毫秒。A 后两对总等待还变长。两者均拒绝进入生产，原始结果见 `shader-comparison.json`、`shader-series-r1/`、`shader-series-r2/`；不把 B 的约 20 秒中位配对等待收益作为可交付收益。

动画隔离比较已完成：枚举的 184 个模型／死亡／形态组合，每个按交替顺序运行原实现、同步合并采样、切片合并采样各三次，共 1,656 次构造。全部半精度骨骼矩阵、双精度挂点、动作表、体型、轮廓和归一化结果精确相等。三轮累计原实现为 7.768 / 7.835 / 7.659 秒，同步候选为 3.841 / 3.758 / 3.822 秒，切片候选为 3.835 / 3.822 / 3.825 秒。该测量包括 CPU 构造及对象包装，排除模型解析与输出哈希，没有 WebGL 上下文；不能直接当成正式整段加载的改善。证据为 `animation-all-r1/` 和 `animation-cpu-comparison.json`。

原型工具的首次清理函数命名冲突导致烟雾检查失败，修正后使用新目录重跑；原失败目录 `animation-smoke-r1/` 保留。集成工具第一次守卫发现遗漏工人／支援模型调用，尚未写入生产文件即退出；补齐调用后才写入候选。已有着色器深度实验中提前释放临时材质的版本也继续保留，不替换为后来结果。

每项最多两种候选；交替至少三对，争议增加至五对。采用必须同时满足收益超过重复测量波动，且总等待、菜单响应、内存和战斗首十秒没有可复现退步。构建时派生缓存、Worker 和按阶段减少入口资源均不是预先承诺采用的改动。

## 采用与拒绝

正式改动仅采用**合并动画采样并分片执行**。同一个原始姿态同时生成所有骨骼图集与武器挂点，直接将原 Float32 骨骼结果转为原来的半精度数据，省去重复姿态遍历和中间大数组。CPU 数据完成后才创建 GPU 对象。切片在姿态之间按约 8 毫秒预算让出，优先使用能力检测后的 `scheduler.yield()`，否则使用计时器；模型解析、单个姿态及同步驱动调用不是可抢占任务，不宣称每次阻塞都小于 8 毫秒。取消、入口代次及 WebGL 上下文代次均在准备过程中检查，旧任务不得发布就绪状态。

动画交替实测为原实现／同步合并／切片合并各三次，顺序 B/P/S、S/P/B、B/P/S，均包含同样的 18 次菜单点击。切片候选相对同组原实现的总等待减少 15.732 / 21.193 / 19.971 秒（12.18% / 15.33% / 13.27%），三次首十秒 P95 均约 16.8 毫秒，JS 堆峰值也均较低。这是诊断构建的单项比较，正式 Web／离线收益另作实测。同步合并候选第三对总等待反增约 28 秒，首十秒 P95 两次退步，拒绝采用。详见 `animation-series-r1-comparison.json`。

缩短开场准备完成五对比较，配对总等待变化为节省 −8.891 / 3.551 / 13.324 / 4.045 / −0.498 秒；中位节省 3.551 秒，对照重复值范围约 9.554 秒、中位绝对偏差约 4.684 秒。菜单虽然更早出现，点击到战斗的等待五次均增加，菜单最大点击往返仍为 3.6–6.3 秒。没有证明稳定总体收益，拒绝采用。

仅 CPU 的可选准备完成三对，菜单最大点击往返降到约 132–168 毫秒，但总等待分别增加 22.699 / 31.512 / 18.963 秒，外部 backing storage 峰值也增加，拒绝采用。详情见 `scheduling-comparison.json`。因此沿用现有开场预算和后台 GPU 准备方式；这是实测后的选择，不是本批强制保留 15 秒。原始着色器与全部 HDR、折射、阴影、首帧就绪校验也保留。

没有新增资源、依赖、Worker、派生缓存文件、存档字段或线上遥测；模型动作采样仍为 24 FPS，运行保存／档案／地图版本仍为 26／6／3。回滚入口为冻结的 0.6.25 源码与实际交付，其他工作流的设计和独立模块不并入本批。
