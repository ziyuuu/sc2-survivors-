## 状态与进入条件

任务状态：`DRAFT → BLOCKED_APPROVAL → READY → IN_PROGRESS → REVIEW → VERIFIED → DONE`。实际阻塞用`BLOCKED`，记录原因、负责人、解除条件；不删除任务冒充完成。`CANCELLED`必须有用户决策引用。

- READY：对应设计版本已批准，依赖已完成，有具体输入/输出/验收/负责角色，原模型或必要资源具备或有可执行核验子任务。
- IN_PROGRESS：把实际执行人/代理写到assignee；只改任务声明的文件和规则，必要扩范围先更新设计。
- REVIEW：代码/文档差异已准备；实际命令与结果已附；失败与未测项明确，不把未来命令写成通过。
- VERIFIED：针对验收矩阵的逻辑/浏览器/离线/人工/性能证据分别满足；人工项必须来自真实检查。
- DONE：设计/数据参考/任务记录一致，相关缺陷已关闭；发布任务还需产物路径/字节/散列。M0的文档完成不代表设计已被接受。

角色：用户为设计最终确认者；主执行者负责整合/运行合同；规则、UI/表现、资源、QA是任务责任类别，不是假定已雇用的团队。可并行代理共享任务号，避免改同一核心文件。每个实现阶段最多3个开发任务并行，整合一次1个。

## 每次开始和结束

1. 读最新用户指示、总计划、决策和当前任务；检查工作区已有修改，不reset/stash/清理用户工作。
2. 从READY挑一项；没有批准的设计时仅推进文档、只读审计和资源核验，不能先实现后请确认。
3. 写明本次触及文件、实际执行人、验证方法。新增问题建立ISS条目，禁止悄悄扩大数值/玩法范围。
4. 完成后先跑相关验证；改配置时再`docs:data`/`docs:check`；适用时交付可玩增量，记录版本及局限。
5. 更新status.json与CHANGELOG；运行`node tools/check-mvp-plan.mjs --write-board`刷新看板，再运行无参数只读检查。
6. 阶段交付摘要：完成/未完成任务、产物、实际检查、风险、下一项；不靠口头“基本完成”跳阶段。

## 变更管理

普通修复遵从已批准行为无需重批。若改变节点效果/资源费用、卡牌次数、英雄数值、无尽规则、素材替代或发布门槛，建立`CR-日期-序号`：旧规则→新规则、原因、影响任务与存档/资源、对应稿件差异、批准人/日期。用户确认后才更新运行数据。

设计批准写入status.json.approvals，包含决策ID、文档revision/hash、用户明确消息摘要与批准时间。助手计划、工具成功、测试通过都不算批准。首次M0批准后不再对同样规则重复询问；新差异才需要新决策。

## 缺陷与发布

严重度：S0存档/资源损失或进退不了；S1必经流程/错误难度/关键单位失效；S2局部表现/性能/输入；S3文案。普通前关60+和原模型交付是发布门槛，不能仅因归S2而忽略。缺陷记录复现数据、版本/种子/难度、期望/实际、根因证据、修复任务、回归场景。

MVP发布需所有M0–M7任务达到DONE，审批记录齐，验收矩阵无关键待验；已知S0/S1为零。有无法满足的条款，明确提交用户决定，不能自行删验收标准。保留当前和上一份已验证可玩包及清单；清理多余产物先确认引用和目标路径，不能删除源资源/存档以凑包体。

## 当前可执行命令

```text
node tools/check-mvp-plan.mjs
node tools/check-mvp-plan.mjs --write-board
```

检查器检查规划结构，不运行游戏、不修改存档或build，也不判定设计已通过。无需安装新依赖或创建外部项目。
