MVP 1–8 是收尾工作包，不等于历史 M1–M7。新工作开始后，在对应工作文档维护一份明确的执行记录，写明包号、当前状态、可运行入口、依据、下一步和阻塞；总计划只更新汇总，不另造互相竞争的进度表。既有机器任务只有实际状态变化时才更新，不能为了整理文档批量标记完成。

## 状态定义

沿用 `DRAFT → BLOCKED_APPROVAL → READY → IN_PROGRESS → REVIEW → VERIFIED → DONE`。确有阻塞时用 `BLOCKED` 并写原因与解除条件；`CANCELLED` 记录实际取消依据。不删除条目冒充完成，也不根据文件名推断状态。

- READY：工作所依赖的规则已明确，输入、输出、验证和负责范围清楚；必要资源已具备或有具体核验步骤。已获得的授权继续有效。
- IN_PROGRESS：记录实际执行者，只改该工作的规则与文件；共享接口变更及时对齐。
- REVIEW：差异和可运行结果已备好，附实际命令、结果及未测项。
- VERIFIED：该范围所需的逻辑、浏览器、离线、人工或性能检查分别有证据；诊断夹具不能替代自然与实体设备检查。
- DONE：该包约定的退出条件全部满足；发布还须绑定实际产物和正式环境结果。独立包通过不等于主游戏接入通过，7A 通过不等于 7B 通过。

用户是设计最终决定者；集成负责人维护共享状态、钱包、生产与保存语义。其他工作线通过约定入口接入同一套正式规则。角色说明不表示已经创建代理或团队任务；给用户拥有的其他聊天发送指令需要直接授权。

## 开始、交付与变更

1. 先读最新用户指示、收尾计划及相关细则，再检查已有修改。保留其他工作线文件，不 reset、stash 或顺手清理未提交内容。
2. 先做已授权且依赖明确的工作。真正缺失的设计语义在依赖它的实现前集中决定，不让无关未定项阻塞 4／5，也不重复索要已有授权。
3. 定下本次改动范围与验证方法。独立入口使用隔离的测试数据，和主游戏导入相同的规则模块；最小真实接入尽早验证。
4. 完成后运行与改动相称的检查；改 `src/data/` 时更新生成参考。记录实际成功、失败和未覆盖范围，不把计划执行的命令写成通过。
5. 更新对应工作记录与必要导航。确实修改旧 `status.json` 后才运行 `--write-board` 刷新旧看板；普通文档整理不刷新历史任务状态。
6. 交付说明写清完成范围、可运行入口、实际检查、剩余问题和下一步。共享代码小批合流，重型浏览器验证与性能测量串行。

普通修复沿用已经批准的行为。涉及新机制、费用语义、存档或验收门槛的变化，记录旧规则、新规则、原因、影响及用户决定；助手建议和工具成功不是用户批准。新想法默认归 1.1；确需扩大 MVP 时按收尾计划换出等量未实施范围或明确重新定范围，不临时增加第九包。

## 证据与文件管理

当前运行底座见 [战斗特效 Final R3 验证](COMBAT_EFFECTS_VALIDATION_20261012.md)，原型和历史版本见各自文档。原始证据按 `reports/local/<主题>-<日期>/` 保存；可提交摘要按现有 `reports/qa/` 约定保存。原素材、交付字节、本地镜像和 Git 同步分别验证。

保留旧文档的日期、来源、实际失败和限制。当前有效文件用索引标注；旧参考以历史用途进入索引，不改写成新版本通过。文件移动前检查工具、文档、清单和其他工作线引用；有引用的保留原址。删除与移动不同，整理不自动授权删除原资源、当前交付、存档或未提交设计。

```sh
node tools/check-mvp-plan.mjs
```
