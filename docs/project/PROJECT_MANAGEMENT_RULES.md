# 项目管理、协作与文档规范

2026-10-27 汇总已有用户要求及现有看板规则。用于新线程接手和日常执行，不新建另一套任务系统，不扩大当次授权范围。

## 入口与信息职责

| 信息 | 唯一维护位置/入口 | 使用方式 |
| --- | --- | --- |
| 长期协作要求与按任务阅读目录 | [根 AGENTS.md](../../AGENTS.md)；[讨论过程](AGENTS_PROPOSAL_20261027.md) 仅作历史 | 放稳定规则，不累计每轮日志 |

| 当前 MVP 收尾/性能任务状态 | [performance-board.json](performance-board.json) | 以 tasks 为任务状态源；历史 baseline/scenes 文字不覆盖最新结论 |
| 人可读看板/计划 | [看板](PERFORMANCE_BOARD.html)、[计划表](PERFORMANCE_TODO.md) | 从 JSON 生成，不直接改两份视图造成分叉 |
| 当前规则和精确数值 | 对应批准设计、当前源码、[数据参考](../GAME_DATA_REFERENCE.md) | 实现差异不能冒充用户批准；数据参考按命令生成 |

用户的最新明确决定覆盖旧方案；历史报告保留原结论及日期，不把旧“未通过”改成“通过”来消除冲突。旧 BACKLOG/status.json 不替代当前看板。后续 1.0 若建立自己的范围/看板，应在入口明确关联与边界，不能无声开启第二个“唯一状态源”。

## 工作闭环

1. **开始前**：读最新用户决定、当前交接、看板与 git status；明确任务 ID、依赖、负责人、范围、验证标准和已有证据。先确认已实现内容，避免按旧计划重复开发。
2. **实施中**：在已授权范围内连续推进。方案仍待体验取舍，先记待讨论；新增确定问题归入现有任务或新增固定编号。风险假设不能直接写成已复现 bug。
3. **验证时**：仅做与改动相关、足以判定结果的检查；需要全回归时执行，不为堆数字重复无效矩阵。复用结果写明版本与范围。
4. **收尾前**：记录实际完成、证据、失败/阻塞、未覆盖范围、下一项及当前 Git/交付状态。更新任务数据和追加记录，再生成两个看板视图，不能只在聊天中汇报。
5. **交接时**：给出当前代码/成品标识、运行入口、未关闭问题、已批准与尚待讨论的范围、相关目录和首个可执行步骤。实现、合流、提交、推送、部署和公开发布分别表述。

当前看板生成命令（在仓库根目录运行）：

```powershell
node tools/render-performance-board.mjs
```

文档/目录维护本身记录在对应整理结论，不为扩大完成数量虚构一个游戏功能任务；若改变既有任务状态，仍必须修改状态源并生成视图。本次规则汇编不更改运维线程当前维护的 V05 状态。

## 状态、并行与完成标准

- 状态使用：待办、进行中、待验证、待讨论、已完成、暂缓。实现完成但尚缺必要验证，标待验证；已完成要满足该项实际完成标准并有证据。
- 同一当前看板最多两项进行中；重型浏览器和 GPU 测量串行，避免互相干扰。该规则不等于自动授权创建子代理或新线程。
- 遇到阻塞说明原因和仍可继续的事项。任务计数不是等权工时、性能完成率或整个 MVP 的验收百分比。
- 按依赖与测量结果排顺序，不承诺未经估算的日历完成日期。备案等待时间是估计，不自动成为发布日期。
- 不通过增加新包、不断扩矩阵来拖延固定终点；确定的结算、存档或明显不可玩缺陷仍需处理，不包装成延期平衡。
- 自动化/物理设备/人类体验分别记录；局部 CPU/GPU 收益不等于整场 FPS 达标，功能批次关闭不等于已知性能问题消失。

## 授权、工作区与分工

- 用户已明确授权的具体工作持续有效，不逐步重复确认；范围外体验取舍或关键缺失信息集中澄清。UI 另须遵守 [具体变更确认规则](UI_RULES.md)，不能从功能授权推导视觉扩改授权。
- 共享目录先辨认已有变更来源；不撤销其他线程成果，不批量暂存全部工作区，不用 reset/clean、强推整理现场。提交范围必须能说明归属。
- 功能改动有需要时使用独立分支/worktree；隔离副本应明确基线和差异。不能以独立原型通过替代正式合流验证，不能只因原型已过时而删除唯一源文件。
- 创建新聊天或向其他线程发消息依据用户授权；本文件不自动启动子代理、其他线程、定时任务或服务器操作。
- 运维负责部署环境与生产数据，功能线程负责其确认范围；避免并发改同一配置、构建输出或任务状态。读取事实不等于取得发布授权。
- 提交、推送、部署、公开发布按相应已获授权执行；包已生成、代码已提交或备案通过不能自动推出后续动作已获授权或已完成。

## 文档、目录与图片位置

- 沿用 [项目目录分工](../PROJECT_STRUCTURE.md)。根 README 讲入口，AGENTS 讲规则与按需目录，交接讲当前事实，日期记录讲当批结果，不在四处复制同一段进度。
- 现有文档/脚本路径被构建与证据引用，优先通过索引整理。确需迁移时核对消费者、唯一输入和完整目标路径，修链接并验证，不按文件夹名字批量移动/删除。
- 项目图片放 D 盘项目目录，不在 C 盘持续积累。生成图归档为 `D:\星际\assets\generated\codex-images`；截图、联系表、验证图放 `D:\星际\reports\local\<topic>-<date>\`；预览源图放对应 preview 目录，下载和中间图也优先使用 D 盘项目路径。
- 工具若使用 `C:\Users\zyuu\.codex\generated_images`，先确认其目录联接实际指向上述 D 盘归档；不把联接当缓存删除、不在旧路径重建实体图片目录。不能仅靠文档声称修改了工具输出行为；确需迁移应逐文件核验后再清原副本。
- 图片归档保留来源/会话目录，不意味着所有图片都属于本项目正式素材；归档不自动进入 Git 或发布包。原始素材、真实存档、会话数据库和其他项目文件不属于项目产物清理范围。
- 原始资源、唯一图稿、源码、测试、构建工具、真实存档与当前使用成品保持。完成且可重建的图片、视频、详细日志、缓存和旧包及时删除，只留简要结论和复现代码；失败也不例外。

## 维护此规范

新增长期规则时记录用户决定和适用范围，更新对应规范及 AGENTS 导航摘要；进度变化更新当前交接/看板。旧规则被替代时写清替代关系，不悄悄删除决策来源。规范整理不能被当成游戏实现、测试或发布已完成的证据。
