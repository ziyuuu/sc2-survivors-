# 300 敌人性能诊断与优化提案

2026-10-16。用户要求先查清约 15 FPS 的瓶颈，再给优化方案，尽量保留怪物密度与画面效果；普通裸装只要求前三关不难。本次完成实际诊断和方案，**没有实施性能优化或修改难度参数**。

结论：当前主要压力来自 CPU 上的原始特效材质／粒子重复计算、单位模拟，以及主场景绘制与阴影。建议先做保持结果一致的计算复用和查询优化，再处理绘制成本。保留 300 活跃敌人上限、4 主力＋4 只 30%＋1 只 50% 的配比及原始模型／特效。

持续交火后的查尔冻结帧有 248 个源特效请求、2,911 个粒子、61 个网格和 15 个折射网格；此时单独源特效 CPU 更新平均约 52.64 ms。它和前面的 10 秒动态样本处于不同战斗时刻，不能把差值全归因于采样器或累积泄漏。工业遗址冻结帧为 197 个请求、1,558 个粒子、51 个网格及 4 个折射网格。

GPU 查询把查尔冻结帧拆为：主场景（含方向光阴影）24.35 ms、接触阴影深度与计算 3.52 ms、折射 1.70 ms、辉光 1.50 ms、最终输出 0.76 ms。GPU 和 CPU 可以重叠；这些 GPU elapsed 区间也可能包含提交间隙，不是 GPU 忙碌周期，不能与 CPU 时间相加或直接反推优化后的帧率。

固定查尔场景的单项诊断中，尺寸减半、停止 contact、停止阴影或停止辉光仍只有约 11–13 FPS；恢复全效果后为 11.85 FPS。完全停止绘制、保留呈现计算也只有 18.28 FPS。它们用于确认成本来源，并非要采用的设置；这批短顺序对照有热机／调度波动，尤其第一次完整 GPU 样本同时开了 CPU profiler，不用它和无 profiler 样本的小差值宣称提速。

## 优化顺序与保留条件

### 1. 先复用源特效材质求值与粒子出生参数

采样栈中，[UnitMaterialSurface.write](../../src/render/materials/unit-material-batch.ts)及其层参数／行写入回调是首要热点。它在[每个特效绘制实例](../../src/render/effects/source/draw-batch.ts)上重新遍历原始材质层、求 UV／颜色／亮度、查组合透明度并写入状态表。当前已经做了 Float32 值比较，但仍会先完成整套求值。

实际单帧计数：29 个活跃特效批次执行 **1,662 次材质 write，按各自材质分组只有 118 组完全相同的 pose／context 输入**。例如一张爆虫死亡材质为 210 次 write／3 组输入，胆汁材质为 60 次／1 组。这是复用机会的计数，不是已经兑现的加速率；各实例行复制、属性更新和上传仍需执行。

建议实现：

1. 在加载时预先解析静态层、固定颜色、组合透明度引用及各 clip 的动态通道，避免每个粒子重建这些关系。
2. 按材质＋**精确**动画时刻＋完整上下文，一帧内只求值一次，再将结果写到需要的实例行；不舍入时间、不改变原始动画频率。单位的攻击叠加、护盾、队伍颜色和活动参数必须进入对应键，不能把源粒子的简单键直接套给全部单位。
3. 对[粒子](../../src/render/effects/source/particles.ts)及[时间轴](../../src/render/effects/source/timeline.ts)，复用由事件、种子、粒子编号和出生时刻决定的局部参数，减少临时向量／矩阵和重复随机哈希。挂点当前变换、当前年龄与颜色包络仍实时计算；缓存随原生命周期释放并设置内存边界。
4. 优化实际数据上传：同一行记录脏区间，碎片太多时回退整行／整表。先以实际上传字节和调用数决定阈值；初始化、扩容及 WebGL 恢复仍走完整数据上传。

保留原模型、所有必要层、粒子数量、轨迹、颜色、寿命、挂点、深度、折射和独立视觉随机流。这一批不通过删粒子或降低特效更新频率取得收益。

### 2. 同步减少单位模拟中的重复资格与邻域工作

真实模拟的采样栈集中在 [World.separation／updateUnit](../../src/simulation/world.ts)、[碰撞](../../src/simulation/movement/contacts.ts)、[光环查询](../../src/simulation/combat/team-auras.ts)与[装备穿越资格](../../src/simulation/starship/controls.ts)。单独模拟诊断的 World.step 采样时间中，separation 约占 22%、contacts.resolve 约占 18%；它们内部还包含装备资格和空间查询，不能再把这些子函数比例叠加。

建议先做三件事：

- 维护真正可能提供光环的源集合，查询时只遍历这些源；存活、位置、视线及目标资格仍读当前值。创建、死亡、升阶、转换阵营／形态需及时更新，保留原遍历顺序与同一 tick 内的语义。
- 没有生效的穿越状态时，直接返回“不忽略碰撞”；避免每对单位都创建数组、查询两个实体并重复检查装备资格。状态生效时沿用完整规则。
- 复用现有空间哈希和地面／空中分桶，减少临时分配及可证实无效的重复判断。已有空间哈希不再算成新方案；不先削减碰撞迭代、近邻数量或 AI 频率。

固定步进仍为 60 Hz，保留攻击、命中、移动、生产与随机数顺序。当前 8 ms 追赶预算在单步已约 12 ms 时容易积压；直接放宽预算会挤压输入和呈现，直接丢掉欠下的步会改变游戏，都不作为本轮优化方案。

### 3. 再处理主场景／阴影提交与 GPU 成本

GPU 查询中主场景占比最高，辉光不是主要矛盾。优先评估：

- 按拓扑／材质变更维护深度与接触阴影参与者，减少每帧多轮全场遍历；静态变换只在真正变化时更新。
- 对重复源特效网格研究同模型、同材质、兼容动画的实例化或姿态共享。粒子和普通单位本来已有实例化，不能重复计算这项收益；透明混合顺序与源动画保持。
- 对确实不影响当前画面、阴影和折射的对象做保守提交剔除，使用完整动画／粒子覆盖范围；保留生命周期及重新进入视野时的正确姿态。
- 对主场景材质重复读取的实例常量、兼容的 UV 仿射变换做有边界的 shader 改进；反射、法线与逐像素项保留原语义。静态阴影缓存只能在光源、镜头拟合、遮挡者都未变化时使用。

原画质下逐项 A/B 后再判断是否需要可选质量档。降低分辨率、减少阴影／粒子等改变画面的策略单独列为后备，不计入上述保持结果一致的收益。

## 普通裸装：范围收窄到前三关

用户的新目标已明确：**普通难度裸装前三关不难即可，不要求裸装轻松完成全部 18 关。** 现有最终弱兵规则下，三族×三种子控制器开场对照为 0/9 存活到 240 秒，全部在第 1—2 关失败；这是固定控制器证据，不是玩家胜率，见[R2 实施记录](DIFFICULTY_R2_IMPLEMENTATION_20261016.md)。

建议后续平衡单独调整前三关的出生生命／伤害入门系数和最初建军窗口，保留当前混合密度、弱兵矿气规则及相对档位。前三关之后用短而连续的过渡接回原曲线；若过渡影响第 4 关，明确记录，不暗改整条普通曲线。困难、地狱和无尽的既定强度本轮保持。具体系数、过渡长度和投放时点仍待候选实测，不在本文件中视为已批准数值。

建议用三族各三种子、零装备／零天赋、正常生产购买救援，跑完完整前三关；保留真实死亡和资源限制，记录阵亡、资源、关卡完成时刻与操作需求，再做普通操作的短试玩。既有“活到某秒”或跳关锁血不替代这个目标。

## 后续验证与本次边界

实施获批后，先在固定地图／种子、同一队伍、同一模拟 tick、同一镜头和效果状态上比较每一批。性能结果使用无 profiler 的独立时段，详细归因另采；同时记录墙钟／tick、真实敌人数、排队数、CPU／GPU、整帧绘制和实际上传。先清除夹具准备对首个 RAF 的污染，再开始稳态采样。不能只看 FPS 而允许模拟变慢。

计算复用核对 World／随机数／命中时刻和逐通道呈现数据；查看受影响密集画面及实际 WebGL 恢复。纯 CPU 复用以相同输入产生相同材质／轨迹结果为目标；GPU 改动逐项检查原图差异和明显显示问题，不引入新的客户端逐帧匹配门槛。普通游玩 60 FPS 目标保持；本次诊断不保证单一优化能达到它，也不代替包 6 合流后的 7B 全内容验收。

原始记录位于 `reports/local/performance-300-20261016/`；[范围化 QA](../../reports/qa/performance-300-diagnosis-20261016.json)绑定两轮成功采样、三个 CPU profile、两张实际截图及当前 bundle。两轮地图身份分别为 `campaign-five-v3:char:768166434:f033be7` 和 `campaign-five-v3:industrial:4242854076:2845f34`；不是相同种子的优化前后实验。冻结对照各自的 time／tick／RNG、实体位置生命动作、飞行与视觉事件指纹一致。浏览器页面／控制台错误为 0，两张截图已查看；未覆盖五图、三族、自然游玩或人类体验验收。

当前工作树的 400 个原构建输入中，397 个仍匹配；`starship/types.ts`、`inventory.ts`、`drops.ts` 已由其他工作更新。此次测量使用未重编译的 R2 bundle，相关热点源码仍匹配；不将此报告冒充包含其他分支最新规则的构建。保留浏览器首次脚本 `__name` 注入失败和 sandbox 启动 EPERM；无修改正式游戏、命名交付、Current、Git 提交／推送或线上发布。
