# Safari 续局资源准备排查与本地候选

2026-10-29，V06-SAFARI-001。用户的 iPhone 17 Pro 在 Coze 首关奖励出现前自动刷新，随后继续游戏在35%再次刷新，并出现浏览器“重复出现问题”页面。本批确认并修复了读档过量准备资源的路径；**原机进程终止原因和首关刷新仍未确认，不能宣布 Safari 故障已解决。**

## 已确认问题与修改

原 `prepareSnapshotAssets` 从本族完整英雄/精英目录开始，并无条件准备无尽资源。普通首关检查点也因此加载大量本局未拥有的身份；公共特效还会扫描存档中的整个装备账户，包括未装备的仓库内容。

候选保留普通生产、敌人及事件依赖，改为补齐存档实际身份、已付订单、候选奖励、英雄复活、精英形态、天赋和已装备舰装未来可能交付的单位。无尽资源仅在无尽或无尽入口检查点准备。装备依赖从待恢复账户读取，避免误用标题页当前账户。解析过程不推进随机数、不修改快照或存档。

画质、UI、玩法数值、保存格式与资源版本保持。修改文件：

- `src/app/snapshot-preload-plan.ts`、`src/app/race-preload.ts`
- `src/render/scene/battle-renderer.ts`
- `src/simulation/starship/asset-plan.ts`
- `test/snapshot-preload-scope.test.ts`、`test/m6-snapshot-assets.test.ts`

## 实测结果

先用实际准备函数截获依赖调用，构造三族合法首关关间状态；这组是直接结束关卡的夹具，不是真实60秒战斗：

| 无英雄、无舰装首关检查点 | 修复前模型键 | 候选模型键 |
| --- | ---: | ---: |
| 人族 | 54 | 28 |
| 虫族 | 32 | 17 |
| 神族 | 41 | 26 |

三族各自无关英雄特效由6组变为0，无尽准备调用由1次变为0。数量不是内存字节，也不包含所有死亡与变形缓存条目。

随后在 Windows Chromium、中画质、模拟“内存容量未知的触屏设备”预算下，自然运行60秒首关，使用模拟方向输入，不改生命、资源或时间。人族、普通、查尔焦土、种子529、无开局英雄/舰装。首关正常结算；存档73,345字节，界面显示170水晶/133瓦斯。关末快照捕获约2.7/1.3ms，结算约9.1ms，档案导出约1.9ms，异步保存约219ms。57秒至关末模型缓存38条、着色器359个，GL缓冲约37.53MB保持；本样本没有发现关末大规模图形分配。

同一浏览器来源、同一检查点，分别以旧准备函数和候选恢复，均完成100%并恢复相同余额、奖励ID与未购买状态：

| 恢复到奖励页后的观测 | 旧逻辑 | 候选 |
| --- | ---: | ---: |
| 模型缓存条目（含死亡/形态） | 114 | 62 |
| 着色器程序 | 591 | 447 |
| Three.js 纹理对象 | 1,727 | 1,227 |
| 可追踪 CPU 数组底层缓冲 | 458,183,346 B | 257,132,520 B |
| 可追踪图片 RGBA 解码估算 | 892,936,192 B | 372,039,680 B |
| 记录的 GL 缓冲分配 | 105,710,330 B | 52,990,880 B |

图片数值是按尺寸估算的解码大小，CPU数组只覆盖可遍历持有者，GL记录不含驱动开销；这些类别不能相加当作进程内存，也不是 iPhone 测量。该次有先后顺序、缓存与后台预备时序差异，模型准备约11.73→3.30秒、最后一轮预热约38.45→4.41秒仅记录为单次观察，不声明稳定加速比例。

最终正式压缩候选另经真实入口恢复：100%后仍为同一奖励页、170/133资源、第二兵营/解锁死神/兵营攻防系统，关键节点警告与错误日志为空，实际截图已查看。正式候选不含检测按钮或诊断注入。
