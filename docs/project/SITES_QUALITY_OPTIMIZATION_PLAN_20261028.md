## 资源调查：开销在哪里

当前路径为：`包下载 → 切片 → GLB gzip展开 → SHA/字节缓存 → Blob URL → GLTF/图片/音频解码 → GPU上传与预热 → 战斗`。

| 静态核对项 | 结果 | 适用边界 |
| --- | --- | --- |
| 资源分发 | 3845条逻辑记录、3742文件、58包；包载荷229.17MB | 十进制MB，不包括入口程序等文件；不是每次必然下载全部 |
| GLB | 282文件，gzip合计130.10MB，展开251.98MB | 解压后仍含编码图片，不等于GPU内存；按请求解一个模型，不是整包所有模型同时解压 |
| 图片 | 外部1499张位图，GLB内1544处图片，最大长边4096 | 全发行内容，不是同屏数量。转换脚本改WebP编码但没有缩尺寸 |
| 潜在重复图片 | 246处GLB内图片与外部图片字节完全一致 | 仅是重复来源候选；GLTF不一定加载每个定义，不能直接认定246次重复GPU分配 |
| 音频 | 1924音频ID、1887唯一文件；`AudioEffects.preload()`解码全部可用声音 | 首次必需入口启动此工作；重置不清除buffers。现有按URL去重已经存在 |
| PCM估算 | 可解析的1886份Opus共4912.98秒，按声道×48kHz×4字节估算1,028,322,940字节，约1.03GB/980.7MiB | 另1份音频未计；实际AudioContext会重采样。不是浏览器RAM实测，也不是“压缩新增了1GB” |
| 菜单包放大 | 728唯一菜单文件载荷30.15MB，落在12包，完整包共48.52MB | 理想每包只取一次；实际HTTP缓存/淘汰可改变传输，不能当线上实测 |
| 入口代码 | gzip7.64MB，展开34.88MB | 还有JS解析/执行开销；设备识别应在轻启动层先给预算，不能等大包和模型全载完 |

`ResourceCache` 已按内容hash保存校验后的资源字节。热缓存命中时可跳过网络和GLB gzip；刷新后图片/音频对象仍通常需要重新解码。因此不能说每次都重复解压，也不能再无预算地加一份“永久解压缓存”。

4包/16包限制只是Service Worker Map条目限制，未统一计算在途下载、切片、展开结果、页面Blob、解码图像、PCM和GPU对象。Map移除在途Promise不等于请求取消；必要时可能出现同包新请求。低画质仍加载不少只在高档使用的资源。需要按用途和字节预算调度。

## 推荐的产品行为

只调整“设置 → 画面”的相关部分，布局、字号和按钮风格延续现状。以下为本次已确认的具体UI清单：

1. 将“特效预设”升级为“画质预设”：**自动 / 高 / 中 / 低 / 自定义**。自动项显示当前选中的档位，例如“自动（中）”；自定义是手动修改子项后的状态。
2. 现有“画质”更名为“渲染分辨率”，与“贴图质量”明确区分；新增贴图质量子项。现有特效与动作设置继续可调，归入同一组高级设置。删除不再正确的“三档均保留屏幕分辨率”说明，不新增大段解释文案。
3. 选高/中/低时，原子应用分辨率、贴图、战斗细节、普通/英雄特效及相应阴影/泛光策略，子项同步显示。手改任一受控子项立即变为自定义，重启保持。运行中的自动分辨率浮动不触发“自定义”。
4. 相机角度、缩放、运镜、震动、血条、字体、音量和操作方式不属于性能档位，不随切档重置。普通/英雄特效在低档受总开关关闭时继续明示禁用。
5. 新安装默认自动。旧用户已有设置迁移为等价手动/自定义状态，保留原生像素选择；用户选择自动后才重新推荐，不能覆盖旧手工偏好。
6. 分辨率/特效可即时应用。贴图换档在主菜单或下一次现有关间准备门内生效，显示一个必要的待生效状态；不在战斗中同时展开两套大资源，不强制刷新丢失当前关进度。

下表是建议的首轮参数，不是已经完成设备调优的承诺；应在试验结果后锁定。DPR指设备像素比，数值只影响3D画布，不缩小DOM界面。

| 项目 | 高 | 中 | 低 |
| --- | --- | --- | --- |
| 渲染比例 | `min(DPR,2) × 1.00` | `min(DPR,1.5) × 0.85` | `min(DPR,1) × 0.70` |
| 世界贴图 | 当前压缩版尺寸与品质 | 约原尺寸1/2，长边≤1024 | 约原尺寸1/4，长边≤512 |
| 战斗特效 | 现有完整策略 | 现有精简装饰、简化阴影/泛光策略 | 现有危险提示优先策略 |
| 单位动作 | 完整 | 完整 | 完整；15Hz仍为手动可选，不自动牺牲动作 |
| UI/文字/肖像 | 保持 | 保持 | 保持 |

世界贴图按语义例外处理：小图不放大、细线/危险范围/队伍色遮罩/法线与图集边界保护；不能统一缩坏可读性。缩小长宽理论上减少像素面积，**不等于整体内存或帧率同比改善**。高档相对当前原生DPR>2也会封顶，旧用户原生选项仍可在自定义保留。

## 推荐实施顺序

### A. 先建立同版测量与统一配置

- 在启动、资源与渲染边界记录有限诊断：网络实际传输、gzip输入/输出/耗时、同包下载次数、图片解码/上传、GLTF解析、PCM已解码字节、在途/驻留字节、长任务、进入可操作菜单/首战/关间时间。保留现有超时、重试和可取消入口。
- 不把现有 `downloadBytes` 当线上的真实压缩传输量，它记录的是SW返回的展开资源字节；需要分别统计包网络字节和逻辑资源字节。
- 建立一份GraphicsPreferences/RuntimeBudget解析器作为启动、设置、资源选择和渲染的共同来源。质量配置与设备硬预算分开：用户手选高画质不等于可以无限并发。
- 体积优化版能力通过构建配置/清单显式传入；淘汰 `update-compressed-game.mjs` 对minified代码中的并发数字做字符串补丁。材质模型hash映射仍需可复现、可核对，不跳过验证。

### B. 在重资源前做自动初选，同时联动画质

- 轻启动层先读取已保存偏好、设备类型线索、DPR、可用的CPU线程数/内存提示，给出临时档位与保守加载预算。设备类型只用于交互与保守先验，不直接决定性能高低。
- WebGL上下文建立后，在大量资源准备之前用小型固定负载采集短时GPU/CPU样本。建议上限约0.5～1秒，优先嵌入已有启动阶段；不跑完整战场压测。精确阈值根据同版设备数据标定，不按“8核=高档”等硬编码下结论。
- GPU扩展、deviceMemory缺失时使用保守候选并允许用户选择；后台页、热启动/着色器编译、节能/热降频导致样本不可信时不升档。保存探测版本，普通刷新不反复跑完整探测。
- 初选在第一批世界贴图请求前完成。GPU负载高时复用现有迟滞控制，仅在当前档位范围内动态降分辨率；运行中不频繁切贴图，不把CPU卡顿误判成必须降分辨率。
- 设备信息只用于本机判断；不增加后台采集字段。触屏笔记本、低配桌面和高性能手机分别覆盖，原操作布局判定独立。

### C. 优先控制解码与驻留，所有档位都受益

**音频按需求准备，应作为第一批性能工作。** 将 `AudioEffects.preload()` 与 `AssetReadinessCoordinator` 的全量音频列表改为当前种族/单位/已选英雄/敌军/装备/支援依赖，加下一关已知内容。常用战斗声进入前准备；对白保持全部可用和既有轮播顺序，只提前解码即将使用的一小段；新身份、召唤、首领奖励在现有必需门内补齐。释放不在用的旧PCM，不能中断活跃音源，不删语音、不改音高/音量、不伪造静音成功。资源预下载只缓存文件，不等于预解码全部声音。

**统一资源调度。** 网络、gzip展开、图片解码、音频解码和GPU上传分别有上限；低档先从1个重解码/1～2路轻任务试验，中档2个、高档2～4个，再由实测修订。首战必需任务优先，可选后台任务在交互/内存压力时让路。保留已做的近期预加载，扩展到低内存桌面，而非只看粗指针。

**按字节管理包和对象。** 在途请求去重Map与可淘汰已完成包LRU分离，以字节而不是包数限额；活动请求不因LRU删引用而失去去重。每个客户端重新握手，SW重启后恢复预算；多标签页使用合并的保守预算。解码缓存、Blob URL和GPU对象按引用释放，避免删除仍由当前材质/音源使用的对象。

**维持已存在的缓存收益。** 保留hash字节缓存并隔离于玩家数据。减少重复完整ArrayBuffer/Blob中间态；在可验证且兼容的边界用流或可转移对象。GLB已在SW解压、GLTFLoader已尽可能使用ImageBitmapLoader，不能把“全部搬到Worker”当作新方案；GLTF对象创建和GPU提交仍需要有节奏地进行。

### D. 制作真正的中低档资源，再按用途重新合包

- 从原始运行时源生成贴图变体，避免在WebP Q70结果上反复有损压缩。高档保留当前压缩资源，模型骨骼、动画、几何和挂点保持；中低档只变贴图相关载荷/引用。外部贴图和GLB嵌入贴图都要覆盖，否则只优化一半。
- 清单采用稳定逻辑ID → 档位变体 → 内容hash/尺寸/依赖，材质profile精确绑定对应变体GLB。请求前解析档位；同一内容不重复存。优先保证身份及错误回退，不用运行时把完整大图解码后缩成小图冒称减少下载和初次解码。
- 按菜单公共、当前地图/部队、声音、后续内容和质量档位组织包；共享内容去重，避免低档为一张小图拉取混装高档资源。首轮以实际依赖图/访问轨迹重排，菜单30.15→48.52MB放大作为可核对的改进点。
- 包名、索引和资源清单都包含版本/hash，旧页面固定旧版本，先上传新资源再切入口，失败保留旧版。缓存键不只用原逻辑ID或`bundle-000.bin`，以免多档混装。
- 对GLB内外相同图像的246处候选先确认实际重复解码路径，再决定是否剥离未使用嵌入图或复用来源；不能未经材质/源动画核对批量删图。

### E. KTX2/Basis只做有限试验，再决定是否纳入

Three.js当前本地为0.186.0，已有可用KTX2Loader，支持硬件能力探测和Worker上限。选一组常用单位、地面、透明特效做WebP与KTX2对照；法线、遮罩、细线、透明边缘和色彩空间单独核对。记录转码成本、GPU格式及回退，不能假设每台设备都得到同样的压缩纹理。

如果有限试验同时证明显存/上传/交互收益和画面可接受，再扩展到适合的资源；否则保留分档WebP方案。几何Draco/Meshopt重新压缩、动画精简、模拟降频、单位减量、整引擎迁移不进入本轮默认方案，它们会引入不同的收益/风险。

## 必须验证什么

1. **设置**：自动/高/中/低/手改自定义/重启恢复；DPR=1/2/3的实际canvas尺寸不同；既有手动偏好、相机、操作和存档保持。高低往返恢复，无重复伤害或技能事件。
2. **资源**：所有变体长宽/hash/依赖检查；冷启动低档不请求高档专有包，改分辨率不能误触发整套资源重载；已缓存刷新不重复网络/gzip，图片和PCM重建分别计数。切档失败保持已可用版本。
3. **预算**：分别报告在途包、展开字节、图像、PCM及GPU估算；测试一次大资源超预算、缓存配额失败、SW重启、多标签页、前后台切换和取消重试。不能只读JS heap就声称测到了总内存。
4. **场景**：固定种子/相同部队的菜单、首次进入、至少1～3关（含原手机反馈位置）、一次有代表性的后期密集段，以及冷/热缓存。每种候选做有限可重复A/B，不展开全目录截图矩阵。
5. **设备**：至少实际低性能手机与参考桌面；模拟DPR/触屏只能验证布局/分支。没有原手机时该崩溃问题继续待验证，不以桌面不崩溃关闭。
6. **收益门槛**：实施前记录同版基线；必须看到低档相对高档请求/解码/上传/PCM预算中对应项目下降，且没有更差的反复停顿、首声缺失或资源遗漏。目标数值在有限试验后锁定，不提前承诺百分比或全场60FPS。

工程交付保留简要结果、复现代码和当前成品；采样日志/截图/缓存按现有保留规则清理。图像与听感最终由用户确认。

## 外部技术依据

- [MDN：deviceMemory](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory)：粗略且并非普遍可用，缺失不能当低/高性能定论。[hardwareConcurrency](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/hardwareConcurrency)也可能由浏览器限制，仅作为信号。
- [MDN：DecompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream)：支持Worker中的流式解压；本项目模型已经走SW，不据此重复提出主线程搬迁。
- [MDN：AudioBuffer](https://developer.mozilla.org/en-US/docs/Web/API/AudioBuffer)说明内存中为32位PCM；[decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)按AudioContext重采样。[RFC 7845](https://www.rfc-editor.org/rfc/rfc7845)提供Opus granule/预跳过计算依据。
- [Three.js：KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)提供能力探测、GPU纹理转码与Worker控制；[MDN WebGL建议](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)区分传输压缩、GPU压缩和小渲染缓冲的收益。文档能力不替代本项目性能实测。

本轮验证边界：静态代码链路、生产比例函数实算、完整现有包字节核对、图片/Ogg头分析和外部官方资料；未声称完成浏览器性能A/B、KTX2原型、视觉验收或手机崩溃复现。
