# Safari 内存说法核实与优化建议

2026-11-09 更新。任务 `SAFARI-20261106`，关联 `V06-SAFARI-001`。本项目的目标是让玩家在 iOS 浏览器连续打多关、进入无尽，并在系统中断后继续同一局。最新决定是把开局内容预排并入苹果优化，由玩法和加载器共用本局计划，见第 10 节。第 8 节记录长局方案，第 7、9 节分别记录读档与换关的 Windows 样本。

## 1. 核实结论

**方向基本正确，但不能把“iPhone 17 Pro 固定 1.5 GB”当成规格，也不能把自动重载直接等同于内存不足。优先降低峰值和无用驻留，再讨论画质取舍；恢复只能减少损失，不能解除系统限制。**

| 截图中的说法 | 判断与证据 |
| --- | --- |
| Safari 有内存硬限制，可能因超限被杀 | 成立，但要区分进程限制与系统整体内存压力。Apple 的 Jetsam 文档明确列出 `per-process-limit` 与 `vm-pageshortage` 等原因，前台被终止也可能表现得像崩溃。[Apple 诊断文档](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports) |
| iPhone 17 Pro 的上限是 1.5 GB | **未找到支持这一固定数字的官方规格。** 2026 年 4 月 Apple 开发者论坛有人提供 iPhone 17 Pro、iOS 26.3/26.4/26.4.1 的内核日志，显示 WebContent 超过 ActiveHard 2048 MB 被终止；Apple 工程师回复确认 iPhone 的 Jetsam 限制比 iPad 更严格。2048 MB 是该报告中的实测限制，不推广为所有系统/页面的统一预算。[原始报告与 Apple 回复](https://developer.apple.com/forums/thread/823061) |

| 打到后面越来越糊是自动降频 | 截图中这是提问者的推测，未见对方验证。硬件降频、帧率下降、降低绘制分辨率是不同现象。本项目确有动态分辨率代码，可解释部分变软，但须核对原机实际启用状态和绘图尺寸；不是 Safari 自动给所有 WebGL 游戏降低画质的证据 |

| 做断线重连就不会出大问题 | 只能部分成立。WebGL 上下文丢失可以尝试重建 GPU 资源；整个页面进程被终止后，原 JS 无法保证再执行保存，只能恢复此前落盘的检查点。移动端 `pagehide` 等事件不保证触发。[Khronos 上下文恢复说明](https://wikis.khronos.org/webgl/HandlingContextLost)、[MDN pagehide](https://developer.mozilla.org/en-US/docs/Web/API/Window/pagehide_event) |

本轮没有找到普通网页可申请解除 iOS 进程限制的通用接口。增加手机总 RAM、安装 PWA、改成 WKWebView 或迁移 WebGPU，都不能据此承诺消除内存终止；这属于方案适用边界，不能作为已验证的替代路线。

磁盘额度与运行内存也不同。IndexedDB/Cache API 的容量、`navigator.storage.estimate()`、添加主屏幕后的存储策略，都不提供网页当前可用 RAM；无需用清空玩家数据验证这条假设。[WebKit 存储策略](https://webkit.org/blog/14403/updates-to-storage-policy/)

## 3. 检索所得方案及采用顺序

### 第一批：先测实际入口、峰值和驻留，不改变画面

**SFR-01：建立同版分阶段账本。** 复用 `view.report()`、`audio.report()`、`httpStore.memoryReport()`、准备队列与现有诊断工具。记录载入/解码/转码/GPU 上传/进战斗/密集战斗/结算/恢复/返菜单的节点；补明确的当前值与峰值、按共享身份去重的字节、用途和持有者。不能把累计 `payloadBytes` 当当前驻留，也不能把 texture/geometries 对象数当作字节。

Apple/WebKit 的 Memory timeline 与 JavaScript Allocations 能定位类别和持有链；它们本身会增加测量开销，须另留不连接调试器的同输入复测。Jetsam 日志负责确认终止原因，不用 JS 堆大小推断 WebContent/GPU 已接近某个固定 1.5 GB 上限。[Web Inspector](https://webkit.org/web-inspector/timelines-tab/)、[Apple Jetsam](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)

**SFR-02：统一重资源阶段的峰值预算。** 当前模型、图片、音频通道各有并发限制，GPU 转码另有 worker 限制；这不等于它们不会同时占用内存。优先测“编码字节 + 图片/PCM 解码 + 模型展开 + 动画图集 + 上传临时副本”是否叠峰，再按预计字节/重阶段做联合准入；无用未来内容延后，有效订单/恢复依赖仍在使用前就绪。

不能简单把 GLTF 加载外层和内部图片解码都套进同一个容量为 1 的锁，外层等待内层会死锁。候选采用按阶段预留/释放额度或可继承的依赖额度；取消、超时、回退及必需资源晋升都释放额度。验收必须同时看峰值、准备耗时、首次开火/技能延迟，而非只追求最低并发。

**SFR-03：在合法边界扩展闲置资源回收。** 先测长局在每关结束后哪些模型、动画图集、公共特效、旧地图或编码 Blob 已无使用者。再考虑把菜单限定回收扩展到可靠的关间/新场景准备边界，并建立公共资源的持有关系与预算。仍存活单位、尸体动画、在途效果、复活、当前装备以及已付生产单都必须保护。已有弱缓存与批次 dispose 复用，不另建重复资源管理器。

Three.js 要求显式处理 geometry、material、texture、render target，删除场景节点本身不够；ImageBitmap 还存在独立 CPU 生命周期。**不能为了省内存一律在上传后 close ImageBitmap 或清空 typed arrays**，必须确认最后使用者及恢复/重新加载路径。[Three.js 释放指南](https://threejs.org/manual/pages/how-to-dispose-of-objects.html)

**SFR-04：按入口补齐音频预算。** 若故障发生在非压缩入口，优先复用压缩路径的分库、按需、共享解码及闲置 PCM 淘汰，避免一开始准备 1,895 个音效文件。压缩入口则核对热音效是否频繁淘汰/反复解码和活跃声音保护。现有 BGM 保持媒体播放，不追加第二套长音轨 PCM；语音是否改流式须按短音频启动延迟与同时播放需求决定。

音频压缩体积不是解码体积。AudioBuffer 使用每样本 4 字节 PCM；例如 180 秒、48 kHz、双声道，样本数据约 65.9 MiB。这是公式例子，不是本项目 BGM 的实际驻留量。[AudioBuffer 文档](https://developer.mozilla.org/en-US/docs/Web/API/AudioBuffer)

### 第二批：有对照收益后再扩大 GPU 压缩

**SFR-05：优先覆盖驻留最大的未压缩贴图。** 对当前 43 张 sidecar 分别验证 ASTC/BPTC 是否真正命中，有没有转码失败后同时留下原图与新纹理、是否在实际格式不支持时正常回退。按当前驻留排名选择后续贴图，不按磁盘文件大小排序。

KTX2 是容器，需要实际转为设备支持的 GPU 压缩格式；普通 JPG/WebP 文件更小不代表上传后同样小。以 2048×2048 RGBA8 为例，含完整 mip 的逻辑数据约 21.3 MiB；若实际为 ASTC 4×4，约 5.3 MiB。格式例子的约 75% 减少不能套作全游戏或进程收益。[Three.js KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)、[PlayCanvas 压缩格式说明](https://developer.playcanvas.com/user-manual/optimization/texture-compression/)

GPU 压缩有损，保持尺寸也不保证逐像素相同。新贴图需要颜色/法线/透明边/遮罩/翻页动画分类型核对；跨材质共享、切档失败回退和 context restore 一并验证。本轮只建议选样，不重新压制资源，也不默认扩展到 UI、文字或危险提示。

### 第三批：画质取舍与恢复体验分别决策

**SFR-06：分辨率只针对像素负载。** 保留现有高/中/低档与动态分辨率范围，先测现有机制。如果确认主要瓶颈为 GPU 填充或渲染目标，才提出新的分辨率/后处理方案和实图对照。不能为修内存悄悄继续降到更糊，也不能用降到 30 FPS 冒充释放静态资源。

普通模型已经使用实例批次与共享资源，不能笼统建议“每个士兵不再复制全部模型”。兵多场景需分别测模拟 CPU、动画/实例数据、效果池与 GPU，按热点优化；不删敌军、丢伤害/积压、取消原版必要表现来达标。1.2 的 CPU 专项与 Safari 进程内存专项分别留证据。

**SFR-07：恢复分两层。** 第一层验证现有 GPU 上下文重建，不改战局、不重复技能/奖励。第二层验证整页重启后继续游戏读取最近已提交检查点，写失败保留旧槽位与备份，保持多页冲突保护。尽力的 pagehide 保存不能提供崩溃瞬间承诺。

如用户希望长无尽轮次也少回退，再提出独立“战斗中周期检查点”设计：保存频率、序列化峰值、特殊关限制、在途攻击/已付订单、拾取/奖励回执、账户与运行状态原子提交，以及旧档兼容都要一起评估。不得仅加定时器抓快照就宣称无损重连。[当前 D05 约定](D05_CHECKPOINT_20261023.md)

## 4. 不直接照搬的网络建议

- **把下载包继续压小。** 有助下载和磁盘缓存，但对展开后的 RGBA/PCM/几何内存未必有帮助；CDN 改善网络失败，也不解除运行内存限制。
- **换 WebGPU 或套一个原生壳。** 可能改善特定渲染路径，但没有证据保证突破 iPhone 进程限制；迁移成本不适合作为当前第一步。
- **照抄 Unity 的 INITIAL_MEMORY/ALLOW_MEMORY_GROWTH。** 本项目主体是 TypeScript/Three.js，不是 Unity 单一 Wasm 堆；Basis 转码有 Wasm，并已有单 worker 与释放机制。WebKit 的 [iOS 18.4 编译峰值报告](https://bugs.webkit.org/show_bug.cgi?id=291677)及 [Safari 26 多线程 Wasm 报告](https://bugs.webkit.org/show_bug.cgi?id=299731)可提示版本/worker 排查方向，但不能据此认定本项目命中相同问题。后者仍列 NEW，工程师关于 worker 终止的解释明确是初步推测。
- **每次变卡自动刷新、清网站数据或强制 GC。** 刷新可能丢进度并重现加载峰值；清网站数据可能删除本地存档；不把这些作为产品常规修复。已有资源缓存清理入口只处理其明确范围。
- **用 Chrome 桌面或桌面 Playwright WebKit 通过证明 iPhone 稳定。** 可定位逻辑/释放错误，不能代替物理 iPhone 的 Jetsam、GPU 驱动及温度/系统压力条件。

## 5. 有限验证计划与通过条件

1. **固定版本与入口。** 记录实际 URL、appBuildId、资源 hash、SW 版本、是否压缩入口、iOS/Safari、画质与实际 DPR、种族/英雄/舰装及存档阶段。线上、1.1/1.2 本地候选不能混用证据。
2. **按原问题走一条短路径。** 首关入场 → 奖励前后 → 继续游戏恢复；另取一段确实兵多的代表场景。冷缓存与热缓存各列，不先做无限自动战役。
3. **定位高占用阶段。** 在 Windows 对照进度、资源准备范围、分配和释放时点。有现场系统日志时，可按时间、进程名和 reason 补查终止类型。
4. **做三次有限生命周期对照。** 同阵容进出/关间转换/恢复，分别记录贴图与缓冲逻辑字节、CPU 数据、PCM、编码 Blob、worker 和进程测量。稳态应回到可解释的缓存区间，不能每轮无界增长；自然 GC 与人工 GC 结果分开。
5. **验证所选优化确实减少对应峰值。** 在同机、同输入、相同缓存条件下比较；至少保证准备时间与首个可操作/首个技能的延迟没有不可接受的倒退。减少对象数或一次更低的 JS 堆读数不足以关闭问题。
6. **异常恢复。** 在 Windows 用 context loss 注入验证 GPU 路径，用隔离账户重开页面验证已提交检查点。采用相同入口、相同存档与相同资源计数比较改动前后的结果。

## 8. iOS 持续游玩的方案选择

### 游戏团队的实际做法

- **Filament Games 在旧 iPad 上做过一小时游玩验收。** 项目针对 iPad 2 / iOS 9。团队整理图集和预载等环节后，平均可玩约 30 分钟，切换活动 10–15 次仍会遇到内存终止。最后他们在大型活动之间保存关键状态、重新加载页面，达成一小时以上的游玩目标。可借鉴的是在安全边界重建会话，这条路径会带来可见的加载停顿。[开发团队复盘](https://www.filamentgames.com/blog/optimizing-your-html5-video-game-a-case-study)
- **Three.js 游戏 Slow Roads 的无限道路复用已经驶过去的几何数据。** 在本项目中对应反复出现的弹道、爆炸、动画实例和绘制缓冲。特效结束归还对象，下次同类效果复用，超过预算的闲置对象在关间释放。池只负责画面，伤害、死亡、奖励继续由模拟结算。[作者案例](https://web.dev/case-studies/slow-roads)
- **Endurance Racing 作者单独排查过 iPhone 首帧预热峰值。** 他报告在 iPhone 13 的 WebGPU 路径调整着色器模块生命周期和最后一次全场景预热绘制，冷启动由五次成功三次改善到五次全部成功。对本项目可迁移的是把预热和第一帧分别计量，保留技能首次实际出现时的画面与响应验收。这项数据属于该游戏的冷启动样本。[作者实测](https://andersonmancini.dev/blog/endurance-racing-iphone-gpu-memory)

## 10. 开局确定本局内容，按关加载

**用户决定**　任务、趣味遭遇、特殊关和随机英雄／精英身份在开局就排好；iOS 据此尽量少加载。建议复用战局种子，在种族、难度、地图、天赋、指定开局英雄和舰装绑定确定时生成一份轻量清单。18 关只写关号、来源、具体内容 ID、出现条件及必要的备选 ID。开局渲染器只取首关需要的资源。玩家仍通过原有操作决定是否进入、购买或领取。

**为何要独立取数**　项目已有 `runConfig.seed`，不少内容仍在触发时调用 `World.random()`。第 3 关首领奖励已经有冻结身份与回执的先例，但抽取使用含本次 runId 的回执，目前在第 3 关才生成。建议用内容规则版本、种子、来源、关号与机会序号确定每个结果；runId 继续服务真实交易与防重复。玩家多打几枪、资源加载重试或先查看第 8 关的依赖，都应得到相同的第 8 关内容。

| 开局排哪些内容 | 后续怎样兑现 |
| --- | --- |
| 自然任务、趣味遭遇、替换虫群 | 排出各关有没有机会、是哪一项、包含什么关键奖励身份。沿用自然事件自第 4 关起的分段概率、难度门槛和避免重复规则。进场时检查安全窗口、地点、现有事件和剩余时间；无法合法落地时按原等待或到期规则处理。酒馆改变类别权重时，按已排的酒馆等级分支选择，玩法与预载持相同结果。 |
| 特殊关门票、传送门及特殊关内部的大模型 | 排出对应关号、入口类型与挑战类型，并把竞技场首领、精英等依赖纳入同一清单。保留玩家领奖／放弃、队伍资格、最多三次和间隔等限制。玩家不领门票时，仅保留还可能由合法传送门触发的依赖。 |

**加载接入**　新局预览与实际开局使用同一份计划，取消、重试和正式提交复用已确定的结果。玩法在对应节点读取该记录，使用成功后才生成原有结算回执。预载读取当前关必需项、已承诺交付及下一关已确定项，从具体身份展开模型、动作／死亡、变形、子体、技能特效、贴图与音效。临近的可选资源在战斗空闲帧或整备时分批准备，已驻留的共享素材跨关复用。下载到本地、解码、GPU 上传分别排期；未来关的条目仅保留小型数据。

优先改动点为 `field-events/pacing.ts`、`special-stages/runtime.ts` 和 `boss-loot.ts` 的内容选择接口，以及 `combat-preload-plan.ts`、`audio-preload-plan.ts`、`snapshot-preload-plan.ts` 和关间后台任务的消费端。当前公共特效从第 3 关起覆盖本族英雄候选，恢复也会扫描快照里的身份字符串。计划应有明确的分关查询接口，避免读档时递归扫描整张 18 关清单、把未来内容重新全部预热。

`asset-readiness.ts` 的压缩版首入场还会枚举可用的 texture / effect-texture，再排除其他地图专属资源。本次清单核对为 192 个 texture、60 个 effect-texture，这是过滤前的条目数。该入口也要消费分关依赖清单。目标是本局用不到的专用资源新增解码和上传为零，多个单位共用的原图只记一次。

**恢复与验收**　新局将计划版本、有限战役表、已兑现槽位及回执纳入既有账户检查点。无尽保留稳定的推导版本与已承诺结果，旧档缺少计划时沿用其原有生成路径，保护已显示的商品、订单和奖励。施工时分别检查同种子同输入重开、不同战斗抽数、不同刷新次数、读档、选择或错过门票；按种族／难度比较内容分布、首次出现关段及合法性。最后同档对照下载与解码的唯一资源、峰值、点击出发到可操作的时间、首个技能与形态是否齐全。以缩小实际加载范围和改善换关等待判断收益。

**已做的小对照**　在普通难度、一名陆军、每张出现的门票都领取的夹具里，使用真实的门票报价函数，对 4 个种子逐关额外消耗 23 次战斗随机数。现行共享抽数的 4 份门票表均发生变化。换用按种子、关号、来源取数的实验入口，4 份表分别保持一致，门票抽取也没有推进战斗 RNG。种子 529 的实验结果是第 5 关横穿虫群、第 9 关资源关、第 16 关横穿虫群。这验证了门票拆分方式；任务、英雄／精英和实际加载收益属于后续接入范围。[复现脚本](../../tools/probe-seeded-tickets.mjs)

## 11. 趣味玩法用完后释放什么

**按资源的最后一个实际使用者释放。** 玩法结束、屏幕不再显示物体、最后一份共享贴图可以卸载，这三个时点可能不同。开局计划提供未来用途，运行时还要核对活着的单位、掉落、正在播的效果、在途加载和图形恢复。

| 例子 | 当前行为 | 建议释放时机 |
| --- | --- | --- |
| 特殊关传送门 | 传送门消失时从场景移除，销毁它独占的几何和材质 | 沿用现有做法，结束即可清理该实例。[特殊关表现](../../src/render/units/special-visuals.ts) |

| 横穿虫群的地面、岩石和雾图 | 退出时渲染器切回主地图，缓存的特殊地图改为隐藏。地形按四种特殊关类型复用，同类型再次进入可命中缓存。地图视图有 `dispose()`；雾图的 `reset()` 只隐藏，小遮罩只有 40×108 | 优先回收计划里近期不会再来的特殊地图视图及其独占资源，同时移除缓存引用。异步创建若在离开后才完成，按当前场景和后续计划决定保留或处置。小雾图可复用，优先核对地图分配和模板持有。[地图切换](../../src/render/scene/battle-renderer.ts)、[场地释放](../../src/render/terrain/flat-map.ts)、[雾图](../../src/render/units/crossing-fog.ts) |
| 挑战结束后带回的部队、装备、奖励 | 特殊关会暂存主战场，并在返回时合并部队状态和结算 | 奖励和已提交进度保留。单位仍在主场使用的本体、变形、死亡动画与声音仍有使用者；只清理挑战专用的表现。[往返与结算](../../src/simulation/special-stages/bridge.ts) |

容易出问题的有四类。第一，已用过的多种特殊地图都保留，首次遇到每个新类型时常驻量逐级增加。第二，主场资源、旧特效与新地图解码／上传同时存在，切场瞬间出现峰值。第三，迟到的加载结果重新写入已经离开的场景缓存。第四，把共享素材过早卸掉，下一关或仍在场的同类对象立即要求重新解码和上传，表现为出发慢、第一次技能卡顿或素材缺失。

实施时，实例退场即时清理；失去最后一个使用者的重型专属资源进入闲置回收队列，结合计划中的下次使用距离与缓存水位分帧回收。保留已有磁盘资源包供再次进入时重建。用“进入→退出→再次进入同类型→进入另一类型”分别核对资源数量、共享同伴可见、首次动作与点击等待。现有道具定向测试 4 项通过，其中验证退出一个宝箱仍保留同伴、传送门独占资源释放、鞘翅消失时移除实例。此次核对的是生命周期语义。[现有测试](../../test/fun-prop-visuals.test.ts)
