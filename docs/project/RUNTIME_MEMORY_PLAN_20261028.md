# 运行内存与入场稳定性优化计划

2026-10-28，归属 V06，计划编号 V06-MEMORY-005。目标是在现有画质、声音和玩法下，降低进入战场的内存与编译峰值，控制切档及跨局后的资源驻留，完成原 iPhone 的稳定性复测。

后续执行与Sites第16版交付见[实施结果](RUNTIME_MEMORY_LIFECYCLE_20261028.md)。以下保留计划制定时的基线、顺序与验收标准；原机验收仍单列。

本轮交付计划。以下实施与新测量均未开始；当前游戏仍采用已发布的 Sites 第15版。已有“验证通过后更新部署”的授权继续有效，具体画质或 UI 取舍按项目现行规则另行讨论。

## A 建立基线与定位峰值

复用现有 `verify-safari-entry.mjs` 及本地检测入口，补齐缺少的分类与阶段标记。诊断只进入本地工具，不新增玩家面板、后台采集或正式HUD字段。

1. **锁定比较输入。** 记录应用与资源hash、浏览器版本、设备、视口、DPR、种族、难度、地图、种子、英雄、装备、存档和实际画质。Windows主样本沿用844×390、DPR 3、触屏模拟、未知设备内存、中档；原机另列。自动档保留并记录实际探测结果，不与强制中档混算。
2. **沿时间线采样。** 记录菜单、完整预下载结束、GLB与图片解码、GPU上传、着色器编译、首次实际绘制、进入战斗、暂停静置20秒、返回标题、再次入场。冷缓存、文件热缓存和同页再次入场分开。
3. **按实际所有者计数。** 统计在途与驻留编码文件、ImageBitmap/像素、压缩mip、几何/索引/姿态数组、PCM、GL贴图/缓冲/渲染目标以及程序数量。共享Source与底层ArrayBuffer去重，注明共享关系；无法准确测量的驱动部分保留为未知。
4. **给峰值定位。** 将资源与编译批次映射到时间线，检查网络/解码/上传/编译是否不必要地重叠，追踪返回标题后仍持有大对象的缓存。程序数不能冒充着色器内存，JS堆也不能代替总占用。
5. **控制试验规模。** 只对主入场路径先做3次基线；候选按同输入交错做3对比较。结果不稳定时最多补2对，仍不明确则记录无确定收益，不无限追加矩阵。冷启动与热缓存各有功能覆盖，只有与候选相关的主条件做重复性能采样。

主报告包含自然运行峰值、静置驻留、准备耗时、首个关键技能的长帧、固定战斗片段p95帧耗时及错误数。人工GC另标为诊断列；不把其结果当正常运行收益。依据基线波动，实施前锁定各阶段主指标、容差及不能接受的耗时退化；不预先承诺固定总内存降幅。

原iPhone可在此阶段先复测第15版，记录准确网址、出错时刻、画质与重载表现。若仍重载，再取该时刻相关的Jetsam/WebKit信息判断是否内存或GPU进程终止；没有系统记录时保留原因未定。PC调查可以继续，不将取得全量私人设备日志设为前置条件。

## B 关闭效果时释放对应缓冲

静态证据：`SceneContact.setEnabled(false)` 和 `ScreenRefraction.setEnabled(false)`主要切换状态；低档泛光主要关闭pass。`warmLightingFrame()`仍会调用折射的 `prepareComposite()`，后者会初始化折射目标。因此需核对**关闭、预热、缩放、恢复**整条路径。实际可节省字节由A测量确认。

- 给每种效果区分启用状态、已分配目标和待恢复状态。关闭时解除相关采样引用，并释放该效果独占目标；保留实际主画面需要的颜色、深度和输出链。
- 关闭的效果在入场预热、动态分辨率或窗口变化时只更新所需尺寸，不重新创建大目标。再次启用时按当前尺寸分配，完成准备后再使用。
- 覆盖暂停中高→低→高、运行后低→高、横竖屏、再次入场及图形上下文恢复。避免首次重新开启出现黑屏、旧深度或错误颜色。
- 沿用已有阴影贴图释放，不重复计收益；释放效果专属缓冲时不能误释放共用的深度、材质或主渲染目标。

**完成条件：** 对应分配记录确实消失，禁用期间不会被后台或预热补回；往返恢复的实际画面与同档基线一致。若切换成本过大，先保留相关资源并记录原因，不以新增等待提示代替修复。

## C 按实际玩法依赖准备公共资源

现有 `commonAssetIds()`按资源类别选出广泛特效，`commonTasks()`准备多族英雄/精英，并执行上传与编译。新的准备清单需要同时服务必需入口和后台准备，避免只收紧一侧、另一侧重新全量载入。

依赖从已有游戏状态和批准规则推导：

| 依赖来源 | 必须包括 |
| --- | --- |
| 活跃部队与所选英雄 | 普通/精英/英雄身份、原生形态、攻击、弹体、命中、技能、召唤、死亡和关联声音 |
| 建筑、订单与救援 | 本局可即时生产的单位、已付订单、降落仓、营救及跨族援军；保留即时可用性 |
| 舰装与天赋 | 已装备效果、连锁触发、特殊弹体、临时召唤、套装以及天赋开启的精英 |
| 当前关与临近内容 | 当前地图、阶段允许的任务/遭遇、敌人与Boss、已经确定的奖励及其形态 |
| 读档 | 存档中仍有效的单位、事件、效果与待结算订单，不能只根据当前可见单位判断 |

对尚未随机确定、却可能在本关即时出现的内容，准备合法候选的完整依赖；不提前抽奖、消耗RNG、改奖励或改变生成时机。已有第三关奖励预定继续复用，不能把全部未来内容重新预定当作资源优化。

实施按“公共底座 → 普通兵种与敌人 → 所选英雄/精英 → 舰装与跨族内容”分批接入。每批同时提供依赖缺项检查，准备失败保留现有可取消、重试与旧资源保护；战斗中不得用空效果或少结算掩盖漏载。

编译继续保留同真实画面一致的必要预热。记录材质变体数、每批耗时和峰值，再缩小批次、让可选工作让路；不照搬其他游戏的“一律不预热”，不把准备开销推给首次释放技能。准备标记需绑定依赖集合、画质和图形上下文代次，失效后不能误报已就绪。

**完成条件：** 当前必需内容与阶段合法候选100%覆盖；不再提前解码/上传未纳入范围的英雄特效。必需入口和后台共享同一判断，预下载仍可只缓存文件。入场峰值或编译耗时有可重复收益，第一场实际战斗的技能、形态、死亡、声音和恢复正确。

## D 按持有关系释放跨局缓存

先追踪模板、实例、材质、共享图片、姿态数组和异步准备任务的持有者，再在现有模块补齐释放。保留 `src/app`、`render`、`assets` 分层，不引入全局通用资源框架或大规模搬目录。

- 区分当前战场必需、近期确定内容和可回收资源；必需资源被固定，不能为了满足预算删除正在使用的模板。资源预算先由A统计确定，延续现有受限设备/其他设备策略，不擅自调整玩家画质。
- 为闲置缓存设置按字节计算的高低水位和最近使用顺序。只在返回标题、关间准备等安全边界回收，避免每帧抖动与刚释放就重载。
- 释放前排空或取消旧代次后台任务，核对活跃实例和共享引用。未完成Promise不能在清理后重新发布旧资源。引用降至零才释放独占资源；最后一个共享使用者退出后才处理共享资源。
- 同步失效模型、公共准备、预热和绑定缓存，保留逻辑ID、内容hash与重建信息。重新进入时从现有文件缓存取回，失败保留可恢复状态。
- 暂停画面、延迟死亡动画和仍有效特效都算活跃使用者；重建只重建呈现对象，不重放伤害、扣费、生产或奖励回执。

**完成条件：** 固定同内容完成3次“入场→退出→再次入场”，相关缓存到达预算内平台，不出现每次增加一份同源资源；另做一次跨族或跨地图重建。允许明确记录的常驻底座，不要求浏览器进程立即回到初始菜单大小。重复载入、声音与保存恢复必须通过。

## E 小范围试验CPU副本释放

该阶段是有条件试验。第15版已释放部分编码副本与转码线程，仍可能保留压缩mip、静态顶点、索引和姿态数据。先计算这些数据的唯一驻留量，再选择收益最大的少量候选。

| 类别 | 处理原则 |
| --- | --- |
| 每帧更新的实例、姿态控制、粒子及CPU查询数据 | 保留；不能清空后再假装无需CPU |
| 共享图片、压缩mip和不可变几何 | 核对克隆、采样变化、重新上传、LOD与恢复的全部读取点后，再决定是否试验 |
| 可按hash可靠重建且已完成上传的不可变副本 | 只有重建流程与失败保护都存在时，才进入白名单 |

当前 `filterTextures()`会改变采样设置并触发 `needsUpdate`；材质克隆、纹理换档与图形上下文恢复也可能重新使用CPU数据。因此不能简单在 `onUpload` 后统一清空数组或关闭ImageBitmap。释放后的任何重新上传必须先有可靠数据，恢复失败不能把已损坏资源标为就绪。

先选一类资源做对照，验证上传完成、共享使用、切档、LOD、重入、context loss/restore以及断网或读取失败。需要常驻CPU查询、没有可靠恢复或净收益小的类别保留原实现。压缩mip若转码后重建代价抵消收益，就不采用。

**完成条件：** 唯一CPU驻留量下降超过测量波动，运行峰值没有因频繁重建变差，所有必需恢复路径通过。E不通过不阻止已独立验证的B至D交付；报告明确记录未采用的试验。

## 有限验证与验收

每批只跑受影响的定向检查；整合候选最后执行 `npm test`、`npm run typecheck`、`npm run docs:check`。不为文档更新重新跑重型游戏矩阵。

| 验证组 | 最少覆盖 | 判定 |
| --- | --- | --- |
| 主路径 | 正式入口完整预下载、自动中档首战、真实第1至3关、热缓存重载、标题后再次开局 | 无页面错误、资源缺失、图形上下文丢失或无故重载；加载与操作反馈有效 |
| 依赖边界 | 三族清单检查；所选英雄/精英与形态；一组舰装触发；订单/救援；第3→4关任务与死亡；跨族援军；代表性后期片段 | 清单断言与实际触发相结合；模型、效果、声音齐全，结算不变 |
| 生命周期 | 高低往返、仅改分辨率、取消/失败回退、后台取消、3次重入、一次跨族/地图、图形恢复 | 无共享资源误释放、旧任务回填或永久空资源；第E批增加读取失败时的恢复 |
| 画面与手感 | 固定镜头下代表性的单位、技能、危险提示和后处理切换；首个关键技能及稳定片段 | 当前档位表现保持；不以少特效、少单位、漏声音或迟结算获得收益 |
| 平台 | Windows Chrome用于A/B；Windows WebKit仅辅助兼容；原iPhone验证真实Safari | 模拟DPR/触屏不充当手机内存与稳定性结论 |

性能收益按每批主指标判定：在3对样本中重复出现，并超过基线自然波动；同时检查入场时间、首次技能长帧和稳定片段p95。只改善GL估算时，只报告贴图/缓冲收益。若主指标无确定改善、出现可复现的耗时退化或任何正确性回归，就撤回该批或缩小范围，不把较长加载换来的低峰值隐去。

原iPhone验收采用正常自动档、既有网址与实际缓存状态，包含完整预下载后入场、第1至3关、返回后再入场及一次前后台切换。建议至少3次独立入场和一次连续第1至3关；次数有限，按实测说明，不宣称长期绝无崩溃。真实用户存档不用于自动化修改，工具使用隔离测试档。

## 交付与回退

1. 每批保留独立、可撤回的源码差异与简要结果。最终候选绑定应用、资源和源码标识，明确哪些代码为共享优化、哪些只在体积优化版启用；共享路径增加原版/离线定向冒烟，不自动更新Coze或阿里云。
2. 用独立 `SC2_WEB_OUTPUT` 生成候选；需要离线验证时明确 `SC2_DEMO_OUTPUT`，保留Current及当前正式成品。发布包排除本地检测页，核对资源依赖、文件hash、压缩回退及版本清单。
3. 工程验证通过后沿用已有授权更新现有Sites与GitHub体积优化版，保持原网址、访问权限、数据库、存档及原存储配置。部署与Git推送分别核验；不自动合并main或新建发布渠道。
4. 原机能访问候选时优先在候选上验证；否则现有Sites工程验证通过的更新可用于原机复测，记录“已部署、实机待验证”。不能以没有原机测试为由把“自动重载已解决”写入交付。
5. 部署后核验真实入口、资源hash、完整预下载、首次入场和再次开局。出现新黑屏、漏资源、无法重建或可复现重载恶化，回退受影响批次/应用至第15版或最近通过版本；保持旧hash资源可用，不清理玩家数据。
6. 更新同一看板与日期记录，保留复现代码、简要数值和当前成品；完成的可重建截图、详细日志、缓存和废弃候选按保留规则清理。

工程批次完成以“采用的改动有收益与恢复证据、候选和线上版本一致”为准。原机缺测时V06-SAFARI-001继续待验证；V06整体仍受原有MVP验收项约束，不因这份优化计划全部执行就自动关闭。
