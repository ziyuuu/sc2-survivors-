## 在原项目切换

1. 解压应用包和资源差量包到新的暂存目录。先完成部署目录/资源目录备份；不要覆盖正在运行的应用文件，也不要上传完整开发仓库中的 `.cache`、`reports` 或私人原素材。若原项目还没有 `active-release.json`，这是首次迁入版本目录，须保留可独立恢复的旧应用备份；更新器不会凭空生成旧应用的版本指针。
2. 在 Node.js 22 以上环境执行，所有占位路径替换为实际路径：

```sh
node <新应用目录>/apply-update.mjs --app <新应用目录> --root <原项目根目录> --assets <原资源根目录> --resources <资源差量目录>
```

更新器复用字节数与 SHA-256 相同的文件，补齐差量，再独立验证全部557个目标资源及所有应用文件。锁定生产依赖在未激活版本内通过 `npm ci --omit=dev --ignore-scripts` 安装；失败不切换入口。完整包ID还覆盖锁文件、部署说明和包内工具，不会因复用同一次Web构建而覆盖当前版本。打包前重新构建Web，确保健康检查的应用ID也对应当前服务器及更新工具。

如果缺少本差量之外的旧资源，更新器停止。应先从原持久目录恢复；只有新版已经推送并确认固定40位提交号后，才可增加 `--commit <该提交号>` 按需补取 Git 中的真实资源。不能用目前旧 main 提交替代尚未发布的新包。

3. 成功后保留 `active-release.json`、`releases/`、`start-coze.mjs` 和原资源目录。原进程重启前仍运行旧版。在原 Coze 项目重新部署/重启，启动命令为 `npm start`。如果平台会重建工作目录，必须把这些已核验应用文件保存在平台真正的发布来源，不能只修改临时容器。
4. 核对 `/health` 与包内 `public/web-release.json` 的 `appBuildId`、`assetReleaseId` 和 `runSchema:23` 一致。完整包ID另见 `active-release.json.packageBuildId`；完整包的逐文件清单另包含锁文件、部署说明等交接内容。

## 后台配置

默认 `SC2_BACKEND_ENABLED=0`，此时静态游戏、浏览器存读及离线版正常工作。新版有 `pg` 依赖，旧文档“无需安装依赖”作废。更新器已在候选版本安装生产依赖；直接运行解压包则先执行 `npm ci --omit=dev --ignore-scripts`。

真正启用采集/后台前，按 [P5 后端交接](P5_BACKEND_HANDOFF_20261006.md) 配置持久 PostgreSQL、精确 HTTPS 源、真实管理主体/联系渠道、备份期限和独立持久删除日志；管理员由部署方通过 CLI 标准输入创建。不要将密码、数据库连接串写入 Git、网页或对话。PGlite 仅用于本机验证，不是 Coze 生产数据库替代品。

仅升级游戏可以保持后台关闭。未提供真实生产配置时，不把本机管理员/SQL验证写成线上后台已启用。

## 升级后检查与回退

逐一检查三族首载与再访、资源失败重试、新局与同schema存读、难度/伤损/付费在途订单、横竖布局、原足下光环与实际弹道。打开管理页不代表后台已配置；后台启用后还须检查授权前零上报、撤回/删除、登录与权限、CSRF、备份恢复前重放删除记录和数据库故障时游戏可用性。

schema14/16的旧开发战局不能续跑为schema23；保留原文件和永久档案，界面按实际格式明确拒绝或提供只读导入处理，不伪造战局兼容。

已有版本指针时，回退可把 `active-release.json.directory` 恢复为其 `previous` 指向的旧版本，同步按旧目录的 `delivery.json` 恢复应用/资源/包身份字段，然后重启，保留资源及数据库。首次迁入且 `previous` 为空时，须恢复步骤1备份的旧应用及原启动配置；不能把空指针当作回退版本。应用回退不回滚永久成长，也不恢复已经删除的个人记录。旧程序不能继续新格式战局。

本机工程、自然战役性能、人工画面与实际 Coze 发布结果分别记录；尚未通过的项目不会因为打包或更新脚本成功而关闭。
