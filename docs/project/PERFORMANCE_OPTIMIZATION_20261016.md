## 绿色喷泉

原 M3 的 `zAcceleration` 是带符号加速度。BanelingDeath 中为负值，旧渲染再次取反，使应向下的加速变成向上，拉长了绿色死亡粒子。字段依据为 [SC2Mapster M3 插件定义](https://raw.githubusercontent.com/SC2Mapster/m3addon/master/__init__.py)及[原始结构说明](https://raw.githubusercontent.com/SC2Mapster/m3addon/master/structures.xml)。修复自由运动和受力积分两条路径，不修改模型、贴图、原始数据或粒子发射量。

真实 WebGL 隔离实验在固定位置同时播放 15 个原 BanelingDeath，年龄为 0.20—0.69 秒。修复前后都为 3,787 个粒子，逐层数量相同；最高世界 Y 从 22.452 降到 5.017。两张原图已查看，高柱消失，原绿液飞溅保留。实验的 time、tick、RNG、地图和所记录的游戏摘要一致；初始相机尚在过渡，未声称两张图的相机或整图一致。它用于验证异常原因，不是自然战斗或性能样本。

证据：`reports/local/performance-optimization-20261016/green-before/` 与 `green-after/`。这两个早期报告顶层 `map: char` 是旧诊断参数命名错误；实际 `initial.recipe` 均为玛萨拉、seed 529。后续工具已修正地图设置，未改写旧报告。

## 三批实现与取舍

1. **材质和粒子复用。** 预索引材质层与组合透明度；同一帧按精确 pose、攻击叠加、护盾、队伍颜色及活动参数复用求值。缓存最多 2,048 组，时间不取整。粒子缓存复用出生时确定的形状、方向、颜色等参数，当前挂点、年龄、包络和运动仍实时计算；最多保留 8,192 个出生记录并清理失活请求。材质纹理按 RGBA 行记录脏区间，最多 8 段且低于整表 25% 时局部上传，否则整表上传；未提交的脏范围保留到真正上传，初始化和 WebGL 恢复完整重传。
2. **模拟查询。** 光环只遍历可能提供该光环的源，查询时仍读取实时存活、阵营、位置、范围和资格；同 tick 升阶、实体替换等会失效重建。无生效装备穿越状态时，在每对接触体查询前直接退出。原有空间哈希、分离／碰撞迭代顺序和 60 Hz 固定模拟保持，本次没有把已有空间哈希算成新增收益，也没有削减邻居或 AI 频率。
3. **场景与阴影提交。** 通过场景子节点增删维护可绘制对象集合，深度、阴影和接触阴影复用集合；材质及可见性仍读取当前值，覆盖嵌套增删、换父节点和材料替换。保持所有原阴影、接触阴影、折射、辉光和原效果。候选中的新网格合批、额外视锥剔除、shader 改写与静态阴影缓存未采用：当前没有建立足够的独立收益及透明／动画等价证据，不将它们写成已完成。

本次收益主要来自 CPU 工作减少。GPU 绘制次数、三角形和冻结场景的上传量均未减少；不宣称本轮已解决 GPU 预算或全局帧率问题。

冻结 FPS 增加 9.0%，原生 FPS 增加 9.6%；模拟没有靠放慢规则取得这项提升，但当前低帧率下约 10 秒墙钟仍只推进不到 2 秒战斗。CPU P95 和 GPU elapsed 未改善，不做稳定性或 GPU 加速结论。CPU 与 GPU 区间不能相加。

早一轮相同旧 bundle 的冻结结果只有 6.05 FPS，早期优化候选为 8.97 FPS；同一旧 bundle 在最终复测为 8.10 FPS，说明热机／调度波动明显。保留这组结果，不用跨轮约 48% 的差值宣传最终收益。当前仍需后续整帧 CPU／GPU 预算工作，原普通游玩 60 FPS 目标不变。

冻结场景两侧均有 4,439 个源粒子、295 个源网格、40 个飘带四边形和 8 个折射网格；缺失层为 0。实际 GL 调用钩子两侧都记录每帧 Float 纹理上传 230,528 字节／348 次，buffer 上传 1,221,960 字节／302 次。冻结的材质本就未变，不能用本轮局部上传实现宣称这一场景减少上传。最终动态区间实际记录 1,402 次材质局部更新；旧版没有同口径的材质专用计数，只确认局部路径已运行，不估算节省比例。

原始 World 记录只有 `expedition.support.stageReceipt` 的新局 UUID 前缀不同；只将这一前缀归一，保留末尾 `:18` 后，所有记录的实体、飞行、事件、资源、敌人机制、排队与出征字段完全一致，time／tick／RNG／地图也一致。未归一的原始摘要和差异保留。A/B 共有 418 个输入，407 个字节相同，11 个本轮文件不同；最终增加两个模块并改用独立入口路径。双方均包含相同的最新共享 UI 和普通入门规则，不混入其他线程差异作为性能收益。

## “自适应”画质

入口为**设置 → 画面 → 画质 → 自适应**，可选，默认仍沿用原设置。只调节战场绘制分辨率，档位为 100%、90%、80%、75%；界面 CSS、镜头、实体、动画及特效数量保持。

使用异步 GPU 计时；持续超过 18 ms 才降一档，连续低于 11.5 ms 达 8 秒后逐档恢复，变档后有稳定期。暂停、加载、后台、失效 GPU 查询不积累压力；不以 CPU 慢直接压低画质。设备不支持 GPU 计时扩展时保持原分辨率。

自动档单独使用较早的 240 步密集场景验证，未混入上述固定画质数据：实际高负载依次 100→90→80→75%，画布为 1080×675，CSS 仍 1440×900，镜头报告及记录的模拟状态一致。进入真实低密度开场后依次恢复到 100%。暂停保持档位，切回清晰立即恢复原画布。随后在清晰档实际触发 WebGL 丢失／资源重备，并检查 960×540、390×844、1440×900 的暂停画面；页面／控制台错误 0。这里没有冒充自动档能达到 60 FPS，也没有把清晰档恢复实验写成自动档开启时的恢复性能测量。
